# Plano técnico: mock da Evolution API nos testes de integração

Atender ao pedido **"identifique os testes de integração e faça um mock da evolution api para esses testes"**, removendo dependência de credenciais reais e de ambiente externo nos testes que hoje exercitam criação/remoção de instâncias.

## Testes de integração identificados

Arquivo atual de integração/manual:

- `tests/test_create_instance_api.py`
  - `test_create_instance_basic`
  - `test_create_instance_with_webhook`
  - `test_create_instance_with_settings`
  - `test_create_instance_dict_format`

Esses testes usam `EvolutionClient` real com `EVOLUTION_API_URL` e `EVOLUTION_API_KEY` vazios e hoje dependem de API externa para passar.

## Arquivos e pontos de mudança

- `tests/test_create_instance_api.py`
  - Substituir configuração fixa de URL/token por fixture que aponta para mock local da Evolution API.
  - Remover fluxo `try/except/finally` com chamadas reais e validar respostas/contratos do mock de forma determinística.
  - Preservar os cenários já cobertos (instância básica, webhook, configurações avançadas e payload em dict).
- `tests/conftest.py` (novo)
  - Criar fixture compartilhada para mock da Evolution API no escopo de teste.
  - Expor utilitário para registrar/consultar instâncias “criadas” e permitir remoção no endpoint de delete.
- `tests/test_client.py`
  - Garantir alinhamento do contrato HTTP esperado (headers e chamadas de `requests`) com o novo mock, evitando divergência entre testes unitários do cliente e integração mockada.
- `README.md` (opcional, se necessário)
  - Atualizar seção de testes para deixar explícito que `tests/test_create_instance_api.py` passa a rodar offline com mock da Evolution API.

## Estratégia de mock da Evolution API

Implementar um mock HTTP in-process (servidor local temporário por fixture) para manter caráter de integração do SDK sem rede externa:

1. Subir servidor local efêmero durante os testes de integração.
2. Implementar rotas mínimas usadas hoje pelo `InstanceService`:
   - `POST /instance/create`
   - `DELETE /instance/delete/{instance_name}`
3. No `POST /instance/create`, responder JSON com estrutura compatível com os asserts atuais (`instance` e/ou `hash` e/ou `qrcode`) e ecoar campos relevantes para validações específicas (ex.: `webhook`, `alwaysOnline`, `readMessages`).
4. No `DELETE /instance/delete/{instance_name}`, responder sucesso consistente (`200` + JSON) para cleanup.
5. Configurar fixture `evolution_client` para usar `base_url` do servidor mock e token de teste fixo.
6. Garantir teardown do servidor após execução para não deixar processo/porta aberta.

## Ajustes de validação dos testes

1. Trocar asserts genéricos por validações explícitas de payload/retorno de cada cenário:
   - criação básica valida `instanceName` e `integration`;
   - criação com webhook valida serialização de `webhook.url`, `byEvents`, `base64`, `events`;
   - criação com settings valida `alwaysOnline` e `readMessages`;
   - criação via dict valida caminho sem objeto `InstanceConfig`.
2. Validar que `remove_instance` é chamado com o `instance_name` correto e que o mock registra remoção.
3. Eliminar `except` genérico nos testes, deixando falhas propagarem naturalmente via `pytest`.

## Algoritmo de implementação

1. Criar infraestrutura de mock HTTP em `tests/conftest.py` com estado em memória para instâncias.
2. Implementar handlers de rota que retornam status e JSON compatíveis com `EvolutionClient._handle_response`.
3. Alterar fixture `evolution_client` em `tests/test_create_instance_api.py` para consumir a URL do mock.
4. Refatorar cada teste de integração identificado para assertions determinísticas sem dependência de ambiente externo.
5. Rodar `uv run pytest tests/test_create_instance_api.py` para validar estabilidade local.
6. Rodar `uv run pytest` para confirmar que a suíte existente continua passando.

## Observações de compatibilidade

- Não alterar chaves externas da API (`instanceName`, `byEvents`, etc.) durante as validações.
- Manter os testes de integração como “integração SDK + HTTP”, mas agora contra mock controlado.
- Evitar mudanças de comportamento no código de produção (`evolution_api_sdk/`); foco desta entrega é camada de teste.
